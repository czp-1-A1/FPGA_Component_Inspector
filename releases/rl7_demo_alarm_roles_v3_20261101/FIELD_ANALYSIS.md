# 全空穴定位孔标签与五连报警分析

基线：R22_RL7_Demo_UIOpt_V2_20261101.bit，Git 83674658，SHA-256 242b9597a6f1fe045dd9c732e56d7ab9320badce9226dcc2c3b67d5ca5593ac5。新分支 codex/rl7-v3-alarm-roles。

## 视频与能确认的现象

用户两段视频都是1280×720、30 fps。第一段572帧/19.067秒，SHA-256 443e1d0362e60e21d8400880b4a179579ce8e5120d2921f17ce2f6e18d6ffb5a；第二段588帧/19.6秒，SHA-256 b8986ef555702a52d602e0ec15041afc350f824c23a1c292d82044138364c333。

第一段约6.0秒显示TOTAL002/EMPTY002/RUNNING；约6.2秒达到004；约6.53秒显示TOTAL005/EMPTY005/FAULT，之后保持FAULT，没有五连红字。底部空穴编号为001～005，复核统计仍000。第二段从开头到末尾一直是FAULT、TOTAL005/EMPTY005，移动载带时圆孔附近出现“待复核”标签；没有一轮新的五连触发过程。

视频没有显示底层F码，因此不能确认本次到底是定位丢失、前后编号不一致还是别的运输故障，也不能仅凭视频证明蜂鸣器引脚的实际电压。FAULT不是五连报警的ALARM，两者需要区分。

用户补充：空穴旁边有有件时通常不出现圆孔标签，整排空穴时容易出现。这与当前检测器使用同帧器件轮廓作为行参考、全空穴时使用固定教学行的结构一致，但不能仅据这一点断言所有环境下的分类失稳原因相同。

## 已用原版源码复现的两条路径

1. 五连报警使用`fifth_empty && healthy`，而healthy包括补件站状态、前后类型签名、定位和编号健康状态。未修改的生产RTL中，健康五连能报警；第5个全局EMPTY与本地LOST、本地编号不确定、P/E签名不一致同时出现时，分别进入F1、FD、F4，alarm_stop均为0；先在第4个后发生F1、随后来第5个有效全局EMPTY，也不报警。`tb_alarm_field_repro`记录了这些结果。这证明逻辑漏洞，不代表已经读出了视频隐藏F码。

2. `frame_shape_search`保留valid=1、kind=1的未知轮廓；计数器只将kind>=2作为器件目标。`compact_inspector_osd.class_char`却把这些未知轮廓也写为“待复核”。合成RGB中，同一器件行Y320有一个真实空穴，上方Y280有定位孔；16×14的标准孔被正确剔除，但12×12的小孔残留为kind1，OSD槽中出现valid1/kind1/Y272..288，同时真实空穴为kind3/Y312..328。这是“圆孔有复核标签但复核计数000”的可复现机制。该RGB是构造试验，未把拍摄显示屏的视频当作原始传感器像素回放。

## 本次修复范围

仅修改`pocket_relay_stop_v2.v`与`compact_inspector_osd.v`；其余636份源文件与UIOpt V2逐SHA一致，包括识别器、计数器、原生图像输入、延迟时基、字库、项目、引脚和SDC。

五连监视独立跟随本RUN连续的全局事件编号；EMPTY累加，PRESENT（含器件复核）清零，重复/跳号/错误RUN/非法类别使监视失效，必须明确新RUN才重新开始。补件站故障不再屏蔽有效的第5个EMPTY；报警锁存并维持电机停止。若此前已FAULT，保留首次故障上下文，同时将界面提升为五连ALARM；K2/K4不能绕过，K3清零或K1明确新RUN清除。

演示左站界面：不显示kind0的非器件标签；kind1未知候选只有中心在教学器件行Y320±16内才显示。kind2的正常/复核器件、kind3空穴在所有行保持显示，行内未知候选也保持显示。底层检测结果和计数输入完全不变。旧DEMO_UI=0界面保持原行为。

此规则解决非器件候选的标签混淆，并未宣称分类器永远不会把圆孔误归kind2/3。后续若圆孔进入有件/空穴/复核统计，应记录实际类别、尺寸和行位置再修识别；不能靠隐藏文字掩盖计数错误。背面、有件/复核波动、冷启动问题继续暂缓。
